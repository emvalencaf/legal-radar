# Does assayer fit legal-radar's evaluation needs?

- **Ticket**: [#3](https://github.com/emvalencaf/legal-radar/issues/3) — Research: does assayer fit this project's evaluation needs? (child of #1)
- **Sources**: `emvalencaf/assayer` cloned and read directly at commit `HEAD` of its default branch (50 commits, latest `Fri Apr 10 2026`, package version `0.1.0`), plus RAGAS and DeepEval's own docs. Every claim below cites a file path in assayer's repo or an external doc URL.
- **Domain terms used below** (`assunto`, `lei`, `jurisprudência`, `doutrina`, knowledge graph vs. LangGraph, `alteração legislativa`) follow `CONTEXT.md` (`docs/context-glossary` branch).

## 1. What assayer actually supports (from source, not the README blurb)

assayer is a real, tested (`tests/` mirrors `assayer/` 1:1, README claims ≥90% coverage target — `README.md`) Python evaluation library built around four abstractions: `Dataset`, `Evaluator`, `Metric`, `Runner`/`EvaluationPipeline` (`README.md` "Core Abstractions"; `assayer/runner/pipeline.py`).

**Metrics** (`assayer/metrics/`):
- Chat quality: `bleu`, `rouge_l`, `bert_score`, `make_semantic_similarity` — corpus-level BLEU (NLTK, whitespace tokenization), ROUGE-L F1 (rouge-score lib), BERTScore F1, and cosine similarity via sentence-transformers (`assayer/metrics/chat.py`).
- Classification: `accuracy`, `make_precision`, `make_recall`, `f1` — thin wrappers around `sklearn.metrics` with macro/micro/weighted averaging and `zero_division=0` handling (`assayer/metrics/classification.py`).
- NER: entity-level per-type precision/recall/F1 and macro-F1 via **exact span matching** — an `EntitySpan(text, entity_type, start, end)` must match all four fields to count as a true positive (`assayer/evaluators/ner.py:86-173`). No partial-overlap or fuzzy-boundary matching is implemented.

**Evaluators** (`assayer/evaluators/`):
- `FaithfulnessEvaluator` — cross-encoder NLI model (default `cross-encoder/nli-deberta-v3-small`) scoring entailment probability of `prediction` (hypothesis) given `reference` (premise), i.e. "is this one predicted text entailed by this one reference text." Falls back to word-level Jaccard similarity if the model fails to load (`assayer/evaluators/hallucination.py:48-221`). This is a **single prediction vs. single reference** check, not a corpus- or graph-aware faithfulness check.
- `LLMJudgeEvaluator` — sends a system prompt + prediction (+ optional reference) to any LangChain `BaseChatModel`, asks for a float 0.0–1.0, parses it with a strict regex (`assayer/evaluators/hallucination.py:224-340`). The default judge prompt is generic ("fully faithful, accurate, relevant" vs "hallucinated, irrelevant") with no legal-citation or entity-grounding semantics built in — but the prompt is fully overridable via `system_prompt`.
- `ConsistencyEvaluator` — wraps any `BaseEvaluator` and runs it **k times on the same input**, then computes agreement rate, Shannon entropy, score stddev, correct-rate, pass@k, recall@k across those k repeated runs, either from historical grouped data or live repeated calls to a `target_fn` (`assayer/evaluators/consistency.py`, `assayer/evaluators/consistency_metrics.py`). This measures **self-consistency / reproducibility of one evaluator or model across repeated trials**, not agreement/contradiction **between two different retrieved documents**.
- `NEREvaluator` — exact-span NER scoring, described above.

**Runner/pipeline** (`assayer/runner/pipeline.py`): `EvaluationPipeline` loads a dataset (list of `{input, expected_output}` or a JSON file), calls `target_fn` per example, routes output fields to named evaluators via `FieldRouter` (maps output dict keys to evaluator names — `assayer/runner/field_router.py`), extracts token usage/cost (`assayer/runner/token_extractor.py`, `pricing.py`), and aggregates metrics. Everything is **synchronous, in-process, per-example**; there's no batch/graph-traversal concept.

**LangSmith integration** (`assayer/integrations/langsmith.py`): pushes each run + its per-field `FieldEvaluation` (method, expected value, obtained value, score, `prompt_hash`) as LangSmith feedback. This is the "audit trail" feature — useful, but it's an experiment/observability sink, not an evaluation method.

**Explicit non-goals** (`README.md` "Non-Goals", `.project/assayer-core/prd.md`): no training/fine-tuning, no built-in UI (LangSmith only), no inference hosting, no billing enforcement, and (from the PRD) no async/streaming and no auth/multi-tenancy in this version.

## 2. Fit against the three evaluation needs in the ticket

### (a) Citation-grounded answers — are citations to lei/jurisprudência/doutrina correct and present?

**Not supported out of the box.** assayer has nothing that resolves or checks a citation identifier (e.g. an `artigo` or LexML URN) against a knowledge-graph node. Its closest primitives:
- `FaithfulnessEvaluator` / `LLMJudgeEvaluator` check free-text faithfulness of a whole answer against a whole reference text — they don't parse out individual citations, check citation existence, or check citation-to-claim alignment.
- `NEREvaluator`'s exact-span matching *could* be repurposed if citations were first extracted as `EntitySpan`s (e.g. entity_type="LEI_ARTIGO") by a separate extraction step outside assayer, giving citation-presence (recall) and precision. But assayer does not do the extraction or the "is this citation correct" (i.e., does the cited `artigo`/`jurisprudência` actually support the claim) check — that would require a custom `LLMJudgeEvaluator` prompt with per-citation context, built by the project, not assayer itself.

### (b) Contradiction detection — does a retrieved doctrine/precedent contradict another retrieved source?

**Not supported.** `ConsistencyEvaluator` is the only component with "agreement" semantics in the codebase, but it measures agreement **across repeated runs of one evaluator on one input** (self-consistency/pass@k), never agreement or contradiction **between two different source documents** (`assayer/evaluators/consistency.py:14-33`, confirmed by `ConsistencySummary`'s fields: `mean_agreement_rate`, `mean_entropy`, `pass_at_k_rate` — all keyed on repeated trials, not on a pair of documents). `FaithfulnessEvaluator`'s NLI cross-encoder *could* be repointed pairwise — feed it `doutrina_A` as premise and `precedente_B` as hypothesis and treat a low/contradiction-leaning NLI score as a contradiction signal — but this would be a bespoke reuse of the NLI classifier, not a feature assayer exposes (no `ContradictionEvaluator`, no 3-class NLI output surfaced — the code only extracts the entailment probability, discarding the contradiction/neutral classes at `assayer/evaluators/hallucination.py:170-197`).

### (c) Multi-hop graph-retrieval quality — precision/recall over graph traversal paths

**Not supported and not in scope.** Every metric in assayer operates on flat prediction/reference pairs or entity spans; nothing consumes a graph, a traversal path, or a set of hops. `recall_at_k`/`pass_at_k` in `consistency_metrics.py` are about repeated-trial label coverage, not retrieval-path coverage over `lei → jurisprudência → doutrina` edges. There is no notion of "expected traversal path" vs. "actual traversal path" anywhere in the codebase or specs (`.project/assayer-core/.specs/`, `.project/consistency-evaluator/.specs/`, `.project/evaluation-pipelines/.specs/` were all read — none scope graph retrieval).

## 3. Complementary tools investigated (primary docs, not just names)

### RAGAS (docs.ragas.io)
- Ships `Context Precision`, `Context Recall`, `Context Entities Recall`, `Faithfulness` (generated response grounded in retrieved contexts), `Response Relevancy`, `Noise Sensitivity` — these are the standard flat-RAG metrics and are more purpose-built for "is the answer grounded in what was retrieved" than assayer's generic faithfulness evaluator (source: https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/).
- RAGAS's **test-set generation** builds a **knowledge graph over the corpus** (chunked into hierarchical nodes) specifically to synthesize single-hop and multi-hop queries, and lets you weight the query-type distribution (source: https://docs.ragas.io/en/stable/concepts/test_data_generation/rag/). This is the closest primary-source match to "multi-hop" in the ticket — but note it's a **test-set generation** feature (produces multi-hop *questions* from a document graph for evaluation), not a metric that scores precision/recall of an *arbitrary* retrieval traversal path against a ground-truth path. It would still need adaptation to score a `lei → precedente → doutrina` traversal specifically.
- No dedicated contradiction-between-sources metric was found in RAGAS's docs.

### DeepEval (deepeval.com)
- `Faithfulness Metric`: checks whether `actual_output` is factually consistent with `retrieval_context` — described in its own docs as centered on "contradictions between the actual_output and retrieval_context" (source: https://deepeval.com/docs/metrics-faithfulness, https://deepeval.com/docs/metrics-introduction). This is closer to citation-grounding than assayer's NLI-based faithfulness because it's designed for RAG contexts specifically (multi-chunk context, not a single reference string).
- `Contextual Precision`, `Contextual Recall`, `Contextual Relevancy`: score the retrieved context set itself against the query/expected output — again flat retrieval, no graph-path awareness.
- `Hallucination Metric`: compares `actual_output` against a fixed ground-truth context (distinct from Faithfulness, which uses the dynamic `retrieval_context`).
- `G-Eval`: a general LLM-as-judge framework with custom evaluation steps/criteria — documented use cases include building a bespoke metric that "extracts claims, verifies them against retrieved information, identifies contradictions, and penalizes hallucinations" (source: https://deepeval.com/docs/metrics-llm-evals, https://deepeval.com/blog/top-5-geval-use-cases). This is a real, documented path to a custom **cross-source contradiction** metric, but still requires the project to author the criteria/prompt — DeepEval doesn't ship contradiction-detection as a named metric either.
- No dedicated multi-hop graph-retrieval-path metric found in DeepEval's docs.

**Summary of the gap search**: neither RAGAS nor DeepEval ships (a) a citation-identifier-level grounding check, (b) a cross-document contradiction detector, or (c) a graph-traversal-path precision/recall metric, as a named, ready-to-use metric. Both give a materially better starting point than assayer for flat context-grounding (RAGAS `Faithfulness`/`Context Precision`/`Context Recall`, DeepEval `Faithfulness`/`Contextual Precision`/`Contextual Recall`), and RAGAS additionally has a documented knowledge-graph-based multi-hop query generator that's closer (though not identical) to graph-retrieval evaluation than anything in assayer or DeepEval.

## 4. Translating the vague briefing terms into measurable criteria

The project's `briefing.md` lists "Citation-grounded answers," "Contradiction detection," and "RAG evaluation" as checklist bullets with no definition. Concrete, measurable criteria, given the domain model in `CONTEXT.md`:

1. **Citation presence** — for each generated answer, extract every citation to a `lei` (`artigo`), `jurisprudência` (`precedente`), or `doutrina` reference. Metric: *citation recall* = fraction of citations in the expected/reference answer that appear in the generated answer; *citation precision* = fraction of citations in the generated answer that exist in the retrieved context set (i.e., aren't fabricated). Both computable as exact-ID-match set operations, no LLM judge required.
2. **Citation correctness (grounding)** — for each citation present, does the cited `artigo`/`precedente`/`doutrina` passage actually support the specific claim attached to it in the answer? Metric: per-citation binary/graded score from an LLM-as-judge (RAGAS `Faithfulness` / DeepEval `Faithfulness`, or a custom prompt) applied **per citation-claim pair**, not to the whole answer — aggregate as mean grounding score and % of citations below a threshold (e.g. 0.5).
3. **Contradiction rate between retrieved sources** — for every pair of retrieved `doutrina`/`jurisprudência` documents used to answer one `assunto`, run an NLI/LLM-judge classification over the pair (entailment / neutral / contradiction, not just entailment probability). Metric: contradiction rate = fraction of retrieved-source pairs classified as contradicting; this needs the full 3-class NLI output (assayer currently discards the contradiction class — see §2b) or an LLM judge prompted explicitly for contradiction, not faithfulness.
4. **Contradiction surfacing in the answer** — when a contradiction exists among retrieved sources, does the generated answer flag it (vs. silently picking one side)? Metric: binary judge score per case where a contradiction was seeded/detected, over a labeled eval set.
5. **Multi-hop graph-retrieval precision/recall** — given an `assunto`, define the expected traversal path/subgraph over `lei → jurisprudência → doutrina` (ground truth curated per test case, or synthesized à la RAGAS's knowledge-graph testset generator). Metrics: *path precision* = fraction of retrieved nodes/edges that are in the expected subgraph; *path recall* = fraction of expected subgraph nodes/edges retrieved; optionally *hop-order accuracy* if traversal order matters (e.g. amendment cascade in `alteração legislativa`). None of assayer, RAGAS, or DeepEval compute this natively — it needs a custom metric operating on the knowledge-graph traversal output, comparing node/edge sets.
6. **Flat-context grounding (baseline RAG quality)** — standard `Context Precision`/`Context Recall`/`Faithfulness`/`Response Relevancy` per RAGAS or DeepEval definitions, as a floor metric independent of graph structure.
7. **Token cost per experiment** — already covered by assayer's `RunResult.cost_usd`/`ExperimentResult.compare` (`assayer/models/run_result.py`, `README.md` "Token Cost Tracking") — keep using assayer for this regardless of the other decisions below.

## 5. Recommendation

**Pair assayer with a complementary RAG-eval library rather than using it as-is or trying to extend it into something it isn't.**

- **Keep assayer** for what it's actually good at and already covers well: the generic evaluation harness (`Dataset`/`Evaluator`/`Metric`/`Runner`), NER-style exact-match scoring (reusable for citation-presence/precision as in criterion 1 above, once citations are modeled as `EntitySpan`s), the extensible registries (`EvaluatorRegistry`/`MetricRegistry` — `README.md` "Extending Assayer"), LLM-as-judge plumbing (`LLMJudgeEvaluator`, fully prompt-overridable), and — importantly — its LangSmith-backed token-cost tracking and audit trail, which neither RAGAS nor DeepEval provide as their primary focus.
- **Add RAGAS or DeepEval** for flat context-grounding metrics (criterion 6) instead of reinventing `Context Precision`/`Context Recall`/`Faithfulness` on top of assayer's single-reference NLI evaluator, which is weaker for multi-chunk RAG contexts. Between the two, RAGAS's knowledge-graph-based test-set generator (https://docs.ragas.io/en/stable/concepts/test_data_generation/rag/) is the more directly relevant primitive for this project given its graph-RAG shape (criterion 5's ground-truth generation), but DeepEval's `Faithfulness`/G-Eval framing is easier to extend into a citation-claim-pairwise metric (criterion 2). A final pick between them should be driven by a small spike, not this research ticket — genuinely reusable pieces on both sides.
- **Build custom, regardless of library choice**: citation-correctness-per-claim (criterion 2), cross-source contradiction detection using the full 3-class NLI output or a dedicated LLM-judge prompt (criteria 3–4), and graph-traversal-path precision/recall (criterion 5) all require project-specific code — no investigated tool ships these as named, ready-to-use metrics. The cheapest path for contradiction detection is extending assayer's `FaithfulnessEvaluator` to expose the discarded contradiction/neutral NLI classes (`assayer/evaluators/hallucination.py:170-197`) rather than building NLI plumbing from scratch, since assayer already wraps the right kind of cross-encoder model — that's a small, targeted extension, not a rewrite.
- **Do not treat "RAG evaluation" as a single metric** — split it into the six measurable criteria in §4 (plus cost tracking) so future tickets can be scoped and tested independently, and each criterion should reference this file rather than the vague `briefing.md` bullets going forward.
